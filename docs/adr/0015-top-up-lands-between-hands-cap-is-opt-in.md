# 补码随时能发、只在两手牌之间落地；带入上限默认不设，设了就两边一起管

`topup 200` 任何时候都能发出去，服务端先收下；筹码在下一手牌开始之前才真正加到 Stack 上，并广播一条 `top_up` 事件。牌局进行中发的补码不会被拒绝，也不会中途改变任何人的筹码。

「只能发生在两手牌之间」是规则，但把它做成「时机不对就报错」会把授时的责任推给客户端：agent 拿不到「现在是不是两手牌之间」这个信号，只能靠猜，猜错就得重试。收下再延迟落地，规则一样守住了，而客户端不需要掐点。这一半没有变过。

## 上限这一半改了：默认不设

原先的写法是「补码后的 Stack 不得超过 `--buyin`」——那个数既是默认带入，也是硬上限。现在上限是 `--max-buyin`，**留空就是不设**，`--buyin` 回归它字面的意思：别人没指定时给多少。

改的理由有两条。

一是**它只挡住了一半**。上限只写在补码那条路上，而 `join` 一分钱不限：一张默认带入 200 的桌，`poker join --buyin 999999` 直接就坐下了。想变成桌上最深的筹码根本不必走补码，绕过去比走正门还省事。一条只在慢路上生效的规矩不是规矩，是错觉——而错觉比没有更糟，因为它让人以为筹码深度是受控的。

二是**默认值站错了边**。真实牌桌用最大带入来压制「随时把自己变成最深筹码」，那是有钱在桌上的场合。这个程序的两种常见用法都不是：本机几个人打着玩，和跑 agent 评测。前者没人需要被保护，后者恰恰常常要故意设置不对称的筹码深度。把一条只有少数场合需要的限制做成默认，代价是多数场合都要先绕开它。

所以现在：默认谁都不拦；真要控制筹码深度就显式 `--max-buyin N`，而那时 `join` 和补码用的是同一条线。要么两边都管，要么两边都不管——中间那个状态是这次要消掉的东西。

## 落地时还要再看一眼，但不许闷声改数

设了上限的话，补码在**落地那一刻**还会再检查一次。这不是重复检查：`handleTopUp` 收下它的时候筹码是一个数，而牌局中途发的补码要等这手打完，那手里他可能赢了一大把。等到落地时回头拒绝一个已经收下的东西更糟，所以这里截断。

但要说出来。这里原先是 `add := min(pending, buyin-stack)`，一声不响地把数改小——而旁边补码被拒时的措辞是「最多还能补 N」，明确承诺过不静默截断。同一条规矩写在两个地方、其中一处还闷声行事，是两个 bug 的温床：一个是行为不一致，一个是没人发现它不一致。现在截断会发一条 `stack_at_max` 说清楚。
