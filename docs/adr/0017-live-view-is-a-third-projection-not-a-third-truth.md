# 人看的那一屏就地重画，但它只是第三种投影

人类客户端对着终端时，把「正在打的这一手」画成固定的一屏，每来一条事件就把光标挪回上一帧开头重画一次，而不是把事件一行一行往下堆。对面不是终端（管道、重定向、文件、测试）时自动退回滚动输出。事件流、JSONL 的字节、服务端的行为一概不动：这一版只是 ADR-0002 那两种投影之外的第三种，源头仍是同一份事件。

「只展示正在玩的」说的是**正在动的那一帧**，不是打完就抹掉。新的一手开始时，刚打完那一手的结尾（摊牌和分池所在的那几行）被搬到屏幕最上面留着，其余清空。留结尾不留开头，是因为回头想看的就是「谁赢了这个底池」；一手打完到下一手只隔 `--hand-delay`，不留的话一闪就没了。只留上一手，再往前的不留——留着就又变回「往上翻三屏找自己的底牌」，那正是这一版要治的病。

之所以要它，是因为滚动那一版把「此刻的局面」和「已经过去的事」混在了同一条时间线上：打到第 14 手时，你的底牌在三屏之外，而决定要不要跟的人需要的是底牌、公共牌、底池、要跟多少——全在眼前，一眼看完。这不是新的事实，是同一批事实的另一种排版。

代价是这一版必须攒状态，而 agent 那条路（ADR-0007）刻意不攒：收到 `your_turn` 就握有决策所需的一切。两者的分工因此要说死——凡是事件里带了权威数值的（座位、底池、公共牌），一律以事件为准覆盖，绝不自己推算。攒状态是为了在轮不到你的时候屏幕上也有东西看，不是为了在客户端重建一份牌局。客户端一旦开始自己算钱，它就会和服务端算出分歧，而 ADR-0003 说了权威只有一个。

「牌桌此刻在等谁」也不自己推。按座位顺序算下一个该谁行动是行得通的，但弃牌、全下、暂离都会让顺序拐弯，推错了屏幕就在骗人——而屏幕说的和服务端认的不一致，正是 ADR-0003 要避免的那件事。所以服务端广播一条 `turn`，跟只给当事人的 `your_turn` 由同一个函数一起生成：一件事实，一个出处，两条事件不可能各说各的。

这件事在屏幕上有两个落点：座位表上那一行的 `行动中…`，和流水的最后一行。两个都要，因为它们服务的是两个时刻——找人的时候看座位表，等的时候眼睛盯的是流水末尾，下一条记录会从那儿冒出来。但它们必须是同一个写法、同一个来源，不然看的人得先认出这两处说的是一回事。流水末尾那一行不进 `v.log`：`v.log` 是这手牌的记录，而「在等谁」下一条事件就翻篇了——混进去的话，上一手留在屏幕上的结尾会以一句永远不会兑现的「轮到某某」收尾。轮到自己时座位表那一行换成 `▶`，`行动中…` 就不再跟一遍：同一行标两次不会更醒目，只是把本来就要塞位置、筹码、本轮投入和底牌的那一行再往折行的边上推一截。

攒状态还把可见性拖了进来：屏幕上的东西是会一直留着的，别人的底牌只要被记进状态一次，就会持续地画出来。所以 `hole_cards` 在这里再认一次收件人，`internal/client/live_test.go` 有一条专门守它——ADR-0006 的不变量不能只靠「服务端不会那么干」撑着。

非终端必须退回滚动输出，这条没有例外余地：光标移动序列只有终端认得，写进管道就是一堆 `\033[12A`，而转录、CI 日志、`| tee`、手牌历史的复盘走的全是那条路。判断只做一次，就是看 stdout 是不是字符设备，和上色共用同一个判断。

重画还反过来约束了客户端的结构：一帧要往回挪多少行，等于上一帧有多少行，而这个数只有在「呈现是单线程的」时候才算得准。所以事件和键盘输入汇进了同一个 `select` 循环，读事件和读 stdin 各自只负责读。用户敲的那一行也要记一笔——终端把它回显之后换了行，不记就每敲一条命令留一条残渣。这也划出了这一版的上限：一帧必须塞得进一屏，塞不进时终端会滚动，「上移 N 行」回到的就不再是原来那个位置。牌局流水因此有行数上限。

没有引 readline，也没有上全屏 TUI 框架。要的不是一个全屏 TUI，是「一屏状态 + 一行输入」，而这一点用几个转义序列就够了；输入仍然交给终端自己的行编辑。代价是输入行没有历史和补全，以及「抢在别人行动时提前输入」那一行的回显会被下一帧盖住（命令本身照发）——后面这条已经基本不成立了，见本文末尾那条修订。判断「对面是不是终端」和「终端多高」这两件事后来交给了 `golang.org/x/term`，理由见 ADR-0018。

## 倒计时，以及它逼出来的局部重画（修订）

`行动中…` 后面跟上这个人还剩多少秒。时限是服务端在 `table` 事件里给的（`timeout_ms`，0 表示不限时），倒计时从广播的 `turn` 事件起算。两处细节必须跟服务端说同一件事：同一个人的第二条 `turn`（他发了个非法动作，服务端把合法动作表重新告诉他一次）不重新计时，因为服务端那边的钟在这种时候也不重置——不然一个只会发非法动作的客户端就能无限拖下去；以及超时之后数字停在 0s，不往负数走，那时候服务端正在替他代打。

轮到自己时不画倒计时，只在「轮到你了」那行静态地写上时限。原因见下面那条：这一屏在你打字的时候不重画，画上去的数字会停在你开始打字的那一刻，而一个不走的秒表比没有秒表更骗人。

倒计时是这一版第一个不靠事件推进的东西，于是它把一条原本能忍的代价顶成了不能忍的：整帧重画会连带抹掉终端刚回显出来的半行命令——以前只在别人行动时偶尔发生一次，现在每秒一次，你打的字每秒消失一次。

所以重画分成了两条路。帧高没变时走局部重画：先 DECSC 存光标（它此刻停在输入行上，列数只有终端自己知道），挪上去把真变了的那几行重写一遍（`\033[K` 清到行尾，免得旧行的尾巴留下），再 DECRC 放回去。输入行一个字节都没被写过，也没有清屏。帧高变了就退回整帧重画——下面的行要整体挪位置，局部重画的前提不成立了。事件也走这条判断，于是白赚一件事：别人弃牌时，流水末尾那行「行动中…」正好被他的「弃牌」顶掉，一出一进帧高不变，你打到一半的命令也就活了下来。

没有因此上 raw mode，也没有上 readline。局部重画只用了两个转义序列就把这件事解决了，而 raw mode 意味着从终端手里接过整套行编辑（退格、光标键、Ctrl-C）——那是另一个量级的东西，ADR 里那句「输入仍然交给终端自己的行编辑」仍然成立。剩下的边界：敲的字多到把输入行挤得换行时，「光标停在最后一行上」这个前提不成立，那一帧会画歪，等下一条事件整帧重画才正过来；`typed` 数行数时是同一个假设。

判卷人也要跟着改。`internal/client/pty_test.go` 里那个玩具终端原先只认三个序列，现在得认五个——漏掉的话它不会报错，只会把转义序列当成几个普通字符画进屏幕，测试照样绿，测的却已经不是那块屏幕了。
