# panic 只留给契约违反，外面进来的一切都走错误处理

分界线是：**这件事有没有可能是别人做的**。

外面进来的一切——命令、动作、数额、名字、JSON——一律走错误处理。动作不合法回一条带机器可读 `code` 的 `error` 事件，轮次仍归他，最多重试三次（ADR-0011）；`ParseCard` / `ParseAction` / `ParseBlinds` 返回 `error`；JSON 坏了、字段缺了，`protocol` 返回 `error`。一个人或一个 agent 无论发什么进来，走的都是这条路，服务端不会因此少打一手牌。

`internal/poker/` 里那七处 `panic` 是**契约断言**，不是错误处理：一手牌至少两个玩家、没筹码的人不能入局、牌堆得够发、`Evaluate` 要五到七张牌、`exec` 不认识的动作、`Draw` 空牌堆（外加只在测试里用的 `MustParseCards`）。这些条件没有任何输入能触发——服务端在调用前全挡住了：`activeSeats()` 滤掉没筹码的，`len(active) < 2` 直接返回，`MaxSeats` 限人数。触发了只说明我们自己的代码错了。

改成返回 `error` 的三个坏处，按要紧程度排：

**它会邀请调用方去「处理」。** 一个 `error` 的意思是「你看着办」，而这里根本不该给选择权——拿着一手只有一个人的牌、或者发到一半的牌堆接着打，结果是悄悄把底池算给错的人。`panic` 说的是「这不可能发生，发生了就停」。这不是偷懒，是在把「不可恢复」这件事写进类型里。

**它会把断言稀释成噪音。** 给状态机最热的路径加一个永远是 nil 的 `err` 返回，每个调用点写一次 `if err != nil`，而那条分支只有在已经有 bug 时才进得去。`exec 收到未知动作` 换成 error，实际形态就是一个 `default:` 分支的返回值——最容易被顺手忽略掉的那种。

**核心没有往外说话的渠道。** `internal/poker/` 没有 IO、没有日志、不 import 任何别的包（ADR-0012）。它的契约只能由边界上的调用方保证，它自己能做的只有在被违约时立刻停下。

## 但进程不该跟着一起没

牌桌 goroutine 里任何没接住的 panic 都会带走整个进程，而手牌历史是异步落盘的——队列里还没写出去的那几手跟着蒸发，**包括出事那一手的种子**，也就是唯一能把这个 bug 原样重放出来的东西（ADR-0016）。

这跟上面的取舍无关：它防不住。你没法 `if err != nil` 掉一个 index out of range，把七处断言全改成 `error` 也一样会死在下一个越界上。所以牌桌 goroutine 的边界上有一个 `recover`，它的职责明确**不是**接着打——状态已经坏了，接着打正是上面要避免的那件事。它只做三件事：把手数和种子记进日志、让历史落盘、干净收桌，然后由 `Close` 把错误报出去，进程非零退出。崩溃于是从「进程凭空消失、二十手历史没了、没法复现」变成「日志里一行，带一个能重放的种子」。

`Stopped()` 这个信号是为它存在的：正常收桌是调用方自己调 `Close`，他知道；崩了的时候没有人知道，没有这个信号，`main` 会挂死在等收尾上。

## 边界本身要被测，不能只靠读代码

「网络上进来的东西碰不到那几处断言」是一句断言，而它是我读代码读出来的。违反它的后果不是报错，是整个进程连同没落盘的历史一起没——这种事不该靠相信。`internal/server/fuzz_test.go` 乱发命令去撞它：不只是坏 JSON（那太容易挡），更是**结构完全合法、顺序和数额离谱**的命令，没轮到就 bet、负数额、大到溢出的数。状态机的坑在这一类里。

真有哪天 fuzz 撞出一个网络可达的 panic，那是个要修的 bug，不是要接住的异常——修法是在边界上把它挡成一条 `error` 事件，而不是往核心里加 `recover`。
